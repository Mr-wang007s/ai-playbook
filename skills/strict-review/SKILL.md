# 强模型对抗式代码审查（Post-Implementation Strict Audit）

当前代码通常刚由轻量执行模型或快速编码迭代完成。你的任务是切换为**严苛、冷静、只看源码事实的资深 Reviewer**，对当前代码变更做全面验收审计。

核心纪律：**不客套、不夸奖、不凑数挑刺。每一个指出的问题必须有确凿的代码路径证据（精确到 `文件路径:行号`）；若确实没有任何实质缺陷，干脆利落地给出 `PASS`。**

---

## 第一步：全量取证与上下文还原（必做）

禁止只扫一眼 `git diff` 的几行片段就开始写评语，必须按顺序收集完整证据：

1. **确定变更全集**：
   - 若用户指定了 commit / 分支 / PR 范围，按指定范围取 diff；
   - 否则默认执行 `git status --short` 与 `git diff HEAD`（兼顾 staged、unstaged，并主动读取本次新增的 untracked 业务/测试文件）。
2. **对齐计划基准（若有）**：
   - 若用户在参数中附带了计划文件（如 `@xxx.plan.md`）或当前对话中存在执行手册（Runbook），读取该文件作为**逐项验收契约**。
3. **读取完整函数与追踪调用链**：
   - 对每个被修改的文件，读取改动位置所在的**完整函数/类上下文**。
   - 凡是修改了函数签名、返回值结构、缓存键、共享状态或公共类型定义，**必须使用全局搜索工具（`Grep`）查找所有上下游调用方**，核实是否引发连锁破坏。

---

## 第二步：五维对抗式审计

详细高频陷阱可按需参考 [references/audit-checklist.md](references/audit-checklist.md)，重点逐一过筛以下 5 个维度：

1. **计划对齐与越界审计（Scope & Plan Fidelity）**
   - 是否修改了计划白名单之外的文件？是否混入了无关格式化、顺手重构或调试残留？
   - 计划要求的每个步骤、红线约束与边界场景是否 **100% 原样落地**？执行模型有没有因为遇到阻力而悄悄删减逻辑、写死硬编码或降级实现？
2. **逻辑正确性与边界态（Correctness & Edge Cases）**
   - 空值（`null` / `undefined`）、空数组/空对象、数值 `0` / 空字符串 `""` 假值误判是否处理妥当？
   - 异步竞态（过时请求覆盖最新状态）、缓存失效与穿透、异常分支下的状态回滚/资源清理是否严密？
   - 是否存在直接原地修改入参/共享引用（浅拷贝污染）的副作用？
3. **爆炸半径与契约兼容（Blast Radius & Contracts）**
   - 公共接口、序列化字段、事件载荷或导出的模块行为变化后，未修改的既有调用方在旧数据或默认参数下是否会崩溃或行为退化？
4. **测试真实性审计（Fake-Test Detection）**
   - **重灾区必查**：新增单测是否真的跑进了被测生产代码的核心改动分支？还是把被测逻辑本身给 Mock 掉了（“测 Mock 自嗨”）？
   - 断言是否足够精确（警惕只断言 `toBeDefined()` / 调用次数，却没断言关键状态结果），负向与边界分支是否真正覆盖？
5. **类型安全与静态规范（Type Safety & Hygiene）**
   - 是否有 `as any`、`@ts-ignore` 强行掩盖类型不匹配？
   - 是否有未使用的导入/变量、吞掉错误的空 `catch {}`、遗留的 `console.log` 或明显违反项目 Lint 规则的写法？

> **注意测试执行规则**：遵循当前工作区关于测试执行时机的规则；若工作区规定不在未经要求时自动跑耗时测试，则先完成深度静态代码审计，并在结论中提示可运行的定向验证命令。

---

## 第三步：输出审查报告

严格按以下精简结构输出中文审查报告：

### 1. 变更对账概览
- **变更范围**：实际改动/新增文件清单（若对照计划，明确说明是否 100% 符合白名单与步骤要求）。

### 2. 审查发现（无问题则直接写“未发现阻塞或潜在缺陷”）

按严重程度分组，每条必须包含 **`文件路径:行号` + 触发条件/根因 + 具体修复方式**：

- 🔴 **Blocker（阻塞级：提交前必须修复）**
  - 逻辑错误、遗漏计划要求、越界破坏公共契约、类型逃逸掩盖真实 Bug、虚假/无效单测。
- 🟡 **Risk / Nit（非阻塞风险或改进项）**
  - 极端边界防御强化、可读性或潜在维护隐患（不凑数，非实质问题不列）。

### 3. 最终裁决（Verdict）
- 明确标记：**`✅ PASS（可直接执行验证并提交）`** 或 **`❌ CHANGES REQUESTED（需修复上述阻塞项）`**。
- 若为 `CHANGES REQUESTED`，在末尾用一句话询问：*“需要我现在直接按上述方案修复这些问题，还是将修改指令交回执行流程？”*
