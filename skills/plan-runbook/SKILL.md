# 编译精确执行手册（Plan to Zero-Ambiguity Runbook）

你的任务是将当前指定的计划文件（或会话中已达成一致的设计方案），在亲自读透源码上下文后，**编译为一份可直接交由弱模型/快模型“零推理、按部就班”执行的精确施工手册（Runbook）**。

核心铁律：**由你（规划侧强模型）在编写手册阶段承担 100% 的源码阅读、调用链追踪、类型对齐与边界推演工作；严禁把任何需要猜测、全局搜索或自行发挥的空间留给执行模型。**

---

## 第一步：强制前置源码勘察（动笔前必做）

在输出或改写计划前，你必须亲自调用工具核实以下事实，严禁凭记忆或猜测编写代码片段：

1. **读取全部目标文件的真实源码**：确认准确的导入路径、函数签名、现有逻辑与锚点行号区间。
2. **闭合上下游契约与类型**：读取涉及的类型定义、调用方与被调用方，确保新增/修改字段、参数与返回值在类型系统上 100% 闭合，绝不编造项目中不存在的辅助函数或外部包。
3. **提取目标文件的代码风格与测试惯例**：
   - 检查仓库 `AGENTS.md` / Lint 配置及同目录现有文件，提取硬性风格约束（缩进空格数、单/双引号、分号、单行最大字符数、禁用的语法如嵌套三元或 `any` 等）。
   - 若涉及单元测试，先读取目标测试文件，复用其现有的 Test Harness / Mock 构造方式，不要另起炉灶发明不兼容的测试脚手架。

---

## 第二步：编写零歧义操作手册

- 若用户在参数或上下文中指定了已有计划文件（如 `@xxx.plan.md`），保留其有价值的背景结论，将其主体原地升级为精确操作手册（或写入用户指定的路径）。
- 若未指定文件，询问或在标准计划路径下创建 Markdown 手册文件。
- 详细章节骨架可参考同目录下的 [references/runbook-template.md](references/runbook-template.md)，必须严格包含以下 4 个核心模块：

### 模块 1：背景目标与严格护栏（执行前必读）
1. **问题与目标**：用 2~4 句话讲清楚要解决的根因与预期行为，必要时附一个精简的 Mermaid 数据流图帮助定位。
2. **修改文件白名单（严禁越界）**：逐一列出**唯一允许修改或新增**的完整文件路径清单，并加粗声明：**“除上述白名单文件外，严禁修改任何其他文件，严禁顺手重构无关代码或升级依赖。”**
3. **编码风格与测试时机约束**：
   - 明确列出前置勘察提取的 Lint 硬约束。
   - **测试执行时机**：明确要求执行模型完成代码与测试文件修改后，除非用户明确指令要求运行，否则不要在每一步中途自动运行耗时的测试或全量检查，统一留到最后按验证清单执行。

### 模块 2：分步精确修改指南（Step-by-Step Atomic Edits）
按编译与逻辑依赖顺序排列（**类型/常量声明 $\rightarrow$ 底层实现 $\rightarrow$ 上层业务接入 $\rightarrow$ 单元测试**），每一步必须满足：
1. **单一职责**：每一步只聚焦一个文件的明确改动，写明**目标文件路径**与**一句话改动原因**。
2. **强制锚点核对指令**：在步骤开头提醒执行模型——*“先读取目标文件确认原代码锚点一致，再执行精确替换；若发现实际代码与锚点不一致，立即停止并向用户汇报，严禁盲猜修改。”*
3. **完整的 `Before`（原代码锚点）与 `After`（替换后完整代码）**：
   - `Before` 锚点必须摘自真实源码（标明大致行号参考），且在目标文件内**唯一可定位**。
   - `After` 代码必须 **100% 完整、可直接通过编译与 Lint**（包含所需的新增 `import`、完整类型声明、空值与边界分支）。
   - **绝对禁止任何省略号糊弄**：严禁出现 `// ... 其余逻辑不变`（除非明确作为不动的最小上下文锚点且边界极其清晰）、`// TODO: 补充实现`、`// 其余场景同理` 等需要执行模型动脑补全的表达。
   - 对于新增的单元测试，必须写出**完整的 `it(...)` / `test(...)` 代码块与精确断言**。

### 模块 3：异常停机准则（Stop Conditions）
明确列出执行模型必须**立即停机汇报、禁止自行绕过**的情形：
- 目标文件的原代码与 `Before` 锚点不匹配；
- 不修改白名单以外的文件就无法解决依赖或类型报错；
- 发现未预料的同名符号冲突或缺失模块。

### 模块 4：定向验证清单（按需或提交前执行）
提供可在仓库根目录直接复制执行的**最小粒度定向命令**（严禁丢一句笼统的 `npm test` 跑全仓）：
1. 定向单元测试命令（精确指定改动关联的测试文件路径）；
2. 定向 Lint 校验命令（精确指定白名单改动文件路径）；
3. 定向类型检查命令（精确到受影响的子包或配置）。

---

## 第三步：自检收尾

输出手册前，快速完成以下自检：
- [ ] 白名单里的每个文件是否都真实读取过？所有 `Before` 锚点是否与当前磁盘源码逐字一致？
- [ ] 把全部 `After` 代码在脑中拼合后，是否有未导入的符号、未声明的字段或超长行等 Lint 违规？
- [ ] 如果把这份手册交给一个不具备跨文件推理能力的轻量模型，它能否不发一问、零自由发挥地一次做对？
